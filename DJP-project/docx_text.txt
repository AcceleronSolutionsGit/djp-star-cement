 STAR CEMENT PJP / DJP AUTOMATION Complete Solution Summary – Phase 1 | Node.js Rule Engine + Admin Panel + API Platform 1. Executive Summary The proposed Phase 1 solution will convert the existing Excel-driven PJP/DJP preparation process into a configurable, API-driven platform. Administrators will upload the required Excel inputs; the system will validate, clean and transform the data into the operational database. A dedicated Node.js Rule &amp; Recommendation Engine will apply the configured business rules and generate user-wise DJP suggestions. SO users can review and edit the suggestions before approval and execution. Actual visit outcomes, including missed or pending visits, will feed back into the next DJP generation cycle. 2. Business Objective Reduce dependency on manual Excel formulas, filtering, VLOOKUPs, copy/paste and manual PJP/DJP preparation. Generate user-wise dealer visit suggestions automatically based on approved business rules. Allow administrators to change formulas, rule parameters, DJP cycle dates and daily dealer capacity without changing application code. Provide a single API layer that can serve the Admin Panel, existing React application and mobile application. Create an auditable feedback loop from planned visits to actual visits and subsequent DJP recommendations. 3. DJP Generation Model Cycle Default Date Range Action C1 1st–15th User clicks Generate DJP; engine uses the latest clean data and configured rules to create suggestions for the first cycle. C2 16th–Month End User clicks Generate DJP again; engine recalculates using till-date execution/performance and missed/pending visit inputs, then creates fresh suggestions. C1 and C2 date ranges must be configurable from the Admin Panel and must not be hard-coded. 4. Daily Dealer Visit Capacity Default business configuration: 8 dealer visits per day per Sales Officer (SO). The value should be configurable from the Admin Panel so the business can change it without modifying Node.js code. Example: if an SO has 18 applicable planning days and the configured capacity is 8, the engine uses the available 8 daily slots subject to eligibility, required visit frequency, working days and other configured rules. 5. Important Source-Based Process Points The available PJP Process Adherence Guidelines state that RSSD &amp; Sub-Dealer customer lists are to be included for SO/SR/MT level visits only; SO-prepared PJP plans require ASM approval; churn uses a 3-month definition; the prospective customer list is shared by the 26th; unplanned prospective visits during the month require ASM approval; and Dynamic PJP review occurs on the 15th using till-date visit information, with revision based on demand and sales conversion and approval from ASM and above. The guideline also records the 28th as the PJP file-sharing date. These source rules should remain part of the final business-rule validation before client sign-off. 7. Excel Upload Processing Architecture Excel files should never be inserted directly into production/master tables. Use a staged processing pipeline: UPLOAD → BATCH CREATION → RAW/STAGING → VALIDATION → ERROR REPORT → CLEANING → TRANSFORMATION → MASTER DATA Create a unique upload batch ID for every upload. Store file name, period, uploader, upload time, row count and processing status. Validate mandatory fields, data types, duplicates, master references and data quality. Reject invalid rows with an actionable error report instead of silently corrupting operational data. Transform valid records into canonical dealer, customer, sales, mapping and visit structures. Keep historical sales and visit records period-wise. 8. Node.js Rule &amp; Recommendation Engine Node.js will be the dedicated processing layer for Excel ingestion, rule evaluation and DJP recommendation. The engine should be modular and configuration-driven rather than a large hard-coded if/else block. Module Responsibility Eligibility Engine Determines which dealers are eligible for recommendation. Classification Engine Determines dealer status/category using configured business rules. Category Engine Handles A/B/C/D or other configured category definitions. Strategy Engine Handles configured market strategies such as GA, GI and MM where applicable. Priority Engine Calculates dealer priority using configured formula/weights. Visit Frequency Engine Determines required and remaining visits by role/status/category. Missed Visit Engine Carries missed/pending visits forward and applies configured priority adjustment. Daily Allocation Engine Allocates available dealer recommendations to daily slots, default 8 per SO/day. DJP Generator Builds the user-wise DJP recommendation for the selected cycle. 9. Configuration-Driven Admin Rule Engine The Admin Panel should allow authorized administrators to change the business logic without changing Node.js source code. Dealer classification formulas/rules. Category thresholds such as A/B/C/D. Market strategy rules. Priority weights and scoring formulas. Visit-frequency rules by role, status, category and strategy. Missed/pending visit priority adjustment. C1 start/end dates. C2 start/end dates. Daily dealer visit capacity. Rule activation/deactivation and rule versioning. All rule changes should be audited with user, timestamp, previous value, new value and applicable rule version where appropriate. 10. Reorder dealer visits. Reschedule visits. Replace a dealer. Add a dealer where permitted. Remove a suggested dealer where permitted. Provide a reason for material manual changes. The system-generated recommendation should remain distinguishable from the user's manual changes for auditability. 13. Approval Workflow SO → Submit → ASM Review → Approve / Reject / Send Back → ZSM / Higher Approval Where Applicable → Published DJP The source guideline explicitly requires ASM approval for PJP plans prepared by SO and states that Dynamic PJP revision requires approval from ASM and above. The exact ZSM approval condition should be confirmed in the final approval matrix. 14. Visit Execution and Missed-Visit Feedback Actual execution becomes an input to the recommendation engine. Planned → Check-in → Visit → Check-out → Completed / Rescheduled / Missed → Store Actuals → Recalculate Next DJP If 8 visits are planned and only 6 are completed, the remaining 2 are recorded as missed/pending and carried into the next recommendation cycle. They should not simply be added on top of the daily capacity; the engine should recalculate the best available 8 slots using the configured priority logic. 15. Click a date to see the dealer list and visit sequence. Plan vs Actual visibility. 16. Development Approach with Antigravity Use Antigravity to build the Node.js Rule Engine and Admin Panel as modular components. Provide each module with explicit input/output contracts, database schema, API specification, validation rules and test cases. Do not ask the code generator to create one monolithic application. Keep the Rule Engine independent from controllers and UI. Start with database schema and upload/staging pipeline. Build Excel validators and importers. Build configurable rule tables and rule versioning. Build each rule-engine module independently with unit tests. Build DJP generation and daily allocation. Expose JSON APIs. Build Admin configuration screens. Build calendar and monitoring. Integrate PHP and mobile/React clients. Add audit logging and duplicate-generation protection. 22. Final Target Process Excel Upload → Clean Database → Configurable Rules → Node.js Recommendation Engine → User-wise DJP → SO Review/Edit → ASM/ZSM Approval → Daily Execution → Actual/Missed Feedback → Next DJP 23. Key Design Principle The Excel files should become input sources, not the application itself. Generate DJP should read clean, validated database data and active rule configuration; it should not depend directly on an Excel file at generation time. This separation makes the platform reliable, auditable, configurable and suitable for future AI/ML integration. 24.
